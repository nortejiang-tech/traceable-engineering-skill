## 1. 核心哲学

复杂项目最容易腐烂的是上下文：为什么选这个方案、究竟验证过什么、上一轮留下什么边界。把决策理由与验证结果变成可追溯文字，使后续的人或 agent 不必重新推导。

方法论服务于项目复杂度。文档的价值是降低未来重新推导的成本；如果没有“未来接手”或昂贵决策，就不要增加仪式。

## 2. 文档层级判定

| 改动性质 | 文档 | 回答的问题 |
|---|---|---|
| 不可逆、跨阶段或推翻后需要重写的架构/产品取舍 | ADR | 为什么这样设计，而不是候选方案？ |
| 可独立验收的功能、重构或验证工作 | STAGE | 做完了吗，证据是什么？ |
| 跨 session、跨人或跨 agent 接力 | HANDOFF | 当前真实状态和下一步是什么？ |

三层可以嵌套：一个 ADR 可展开为多个 STAGE，一轮工作可跨多个 STAGE，结束时用 HANDOFF 收敛。三层不要求同时存在。

## 3. 状态与证据模型

使用三态：

- `PASS`：已经执行与目标匹配的验证，证据支持结论。
- `FAIL`：已经执行有效验证，证据反驳预期。
- `INCOMPLETE`：证据不足、验证未运行、验证边界排除，或工具/环境阻断了结论。

多个子项的总体状态取最弱子项。任何必需项为 `FAIL`，总体为 `FAIL`；没有 `FAIL` 但存在 `INCOMPLETE`，总体为 `INCOMPLETE`；全部必需项为 `PASS` 才能总体 `PASS`。

证据至少回答：

1. 验证对象是什么版本、工作区或产物？
2. 运行了什么命令或操作？
3. 退出码、测试计数、日志、截图或产物路径是什么？
4. 验证的是源码、构建产物、安装包、真实运行态还是物理设备？
5. 哪些内容没有验证？

把以下结论分开：

- **被测对象失败**：有效测试触发了产品或代码缺陷。
- **工具失败**：脚手架、参数、模型 ID、依赖或测试工具本身失败，不能推出被测方案不可行。
- **环境失败**：权限、网络、证书、设备或服务状态阻断验证。
- **证据缺失**：只有总结或预期，没有可复查结果。

## 4. 十条工程原则

### P1 — 任务书先于代码

先写目标、约束、验收标准和验证边界，再实施。把设计分歧留在修改文字仍然便宜的阶段解决。

### P2 — 状态诚实

不要用一个通过的子项掩盖失败或未验证的子项。`INCOMPLETE` 是独立状态，不是委婉的失败，也不是可忽略的成功。

### P3 — 区分工具失败与对象失败

方案没有跑通后，先定位失败层。只有测试路径有效，才能用结果评价被测对象。

### P4 — ADR 与任务状态分离

STAGE 记录“是否做完”，ADR 记录“为什么这样设计”。如果推翻需要重写而不是重改，创建 ADR。

### P5 — 显式声明范围边界

每个 STAGE 都写“本轮做什么、不做什么、验证什么、不验证什么”。显式排除不是疏漏。

### P6 — 契约演进优先使用加法

共享契约新增版本或字段时，保持旧调用方有效，并通过归一化把旧格式映射为新语义的特例。没有迁移计划时不要破坏性改写字段含义。

### P7 — 失败显式，成功不可伪造

异步或跨进程操作只有在真实后置条件成立后才能报告成功。发送消息、进入队列或启动流程不等于目标完成。

### P8 — 不确定时保守失败

数据不完整或状态不明时，等待、隔离、拒绝或丢弃，不猜测性拼出“看起来成功”的结果。可追溯性优先于表面覆盖率。

### P9 — 让边界可确定性测试

用依赖注入隔离权限、时钟、网络、音频会话和外部服务，使时序、并发与失败边界能用 fake/mock 稳定复现。真机或真实环境验证聚焦物理边界，而不是替代逻辑测试。

### P10 — 交接是一等产物

不要要求接手者重读全部对话、diff 或 git log。用自包含 HANDOFF 固化当前事实、验证矩阵、架构心智模型、技术债和下一步。

## 5. 主会话与 Coder 分工

主会话承担：

- 重建事实、澄清目标并做架构规划。
- 定义 ADR、阶段依赖、设计不变量和验收矩阵。
- 为当前阶段生成自包含的 Coder 提示词。
- 独立检查 diff、验证结果与交付运行态。
- 在证据表明委派质量不足时提出接管申请。

Coder 承担：

- 只实施当前 STAGE 的授权范围。
- 保护现有与无关改动，不自行扩展目标。
- 运行指定验证并返回原始证据。
- 遇到架构分歧、范围冲突或停止条件时暂停并报告。

主会话与 Coder 应是两个职责分离的会话。Coder 可使用用户指定的较低成本实现模型；模型名称属于会漂移的产品状态，先确认当前可用型号，再给出选择建议，不把历史型号写成硬依赖。

一次只向 Coder 暴露当前阶段的可执行细节。后续阶段只保留为依赖和边界，避免为了“完成整个计划”而提前修改未授权区域。

接管不是默认升级路径。优先给出一次边界明确的修正提示词；若架构不变量被破坏、同类问题重复、高风险跨模块推理超出 Coder 能力或证据可信度不足，再以具体证据申请用户批准主会话接管。

## 6. 适用边界

以下情况通常值得使用：

- 决策需要跨 session 保留。
- 错误代价较高，或推翻需要重写。
- 多个人、agent、设备、语言或服务共享契约。
- 验证包含模拟器、真机、安装包、线上服务等不同证据层。
- 工作需要多阶段依赖和明确交接。

以下情况通常不值得完整使用：

- 一次性脚本或纯探索 spike。
- 两小时内可完成并当场验证的小修复。
- 可随时回滚、没有下游依赖的局部实验。
- 不会跨 session、不会交接、也没有昂贵决策的工作。

对于轻量任务，保留目标、边界和实际验证即可，不创建完整 ADR/STAGE/HANDOFF 体系。
